## Goal

Build a local, read-only Model Context Protocol (MCP) server that provides intelligent, contextual, and historical code review assistance for repositories across the UFS-Chem ecosystem:

1. **Local MCP Server over STDIO**: Easy to run locally against a PR created on GitHub (or a local git diff). Exposes MCP tools, resources, and prompts to any MCP-compliant client (Claude Desktop, Cursor, Antigravity, VS Code Copilot Agent, Gemini CLI).
2. **Zero Runtime LLM inside the MCP server**: Following `omd-docs-mcp`, the server does **not** invoke any local or remote LLMs during retrieval or evaluation. It serves deterministic, classified historical evidence, rule-based audits, and structured context so the user's *chosen client LLM* performs the final synthesis without redundant latency, cost, or hidden hallucinations.
3. **Historical PR Knowledge Base (SQLite + FTS5)**: Scans, parses, and indexes historical PR comments, discussion threads, reviewer identities, and diff follow-ups across 5 core repositories:
   - `ufs-community/CATChem`
   - `ufs-community/CECE`
   - `ufs-community/ufs-chem-container`
   - `benkozi/ufs-chem-assay`
   - `bbakernoaa/HELM-Project`
4. **Follow-Up Diff Tracking & Criticality Scoring**: Tracks whether a historical comment prompted a code change in subsequent commits (`has_diff_followup`) vs mere discussion, along with language detection, reviewer identity, and criticality ranking (1 to 5).
5. **Ponytail & UFS-Chem Domain Review Rules**: Integrates over-engineering review heuristics from the `ponytail` skill (`delete`, `stdlib`, `native`, `yagni`, `shrink`, net lines removable) alongside UFS-Chem domain checks (CCPP physics interfaces, NUOPC cap conventions, ESMF state sharing, chemistry unit conversions, mass conservation, and MPI/OpenMP concurrency).
6. **Flexible Output Formatting for the Client LLM**: Provides structured tools and schemas enabling the client LLM to format review findings either as:
   - GitHub API-compliant JSON review comment payloads ready to post directly to GitHub (`/repos/{owner}/{repo}/pulls/{pull_number}/reviews`).
   - Clean, readable GitHub Flavored Markdown for human review or pasting into comments.
   - Always accompanied by a critical summary highlighting high-risk catches and over-engineering findings.
7. **Configurability & Refresh Automation**:
   - Source repository list is configurable via YAML/JSON.
   - Built-in incremental sync CLI command (`ufs-chem-pr-review-sync`).
   - Weekly GitHub Actions CI job to refresh the database.
   - Strict 100% code coverage requirement in CI for mock unit tests; integration tests with live network connections are isolated behind `@pytest.mark.integration` and deselected by default.

## Pre-design audit (fresh facts, 2026-10-07)

1. **Reference Package Inspection (`bbakernoaa/omd-docs-mcp`)**:
   - Uses `mcp>=1.12,<2` (the official Model Context Protocol Python SDK).
   - Python requirement: `>=3.11`.
   - SQLite (`sqlite3` standard library) with committed local database (`data/nuopc.sqlite3`).
   - Zero LLM in the retrieval loop: original evidence, release provenance, and citations are returned directly to the agent.
   - Architecture separates ingestion (`ingest.py`, `fetch_*.py`) from server serving (`server.py`, `knowledge.py`).
2. **Reference Harness Inspection (`benkozi/ufs-chem-assay`)**:
   - Tooling: `uv` for dependency management, `hatchling` build backend, `ruff` (check & format), `mypy` with `pydantic.mypy`, `yamlfix`, `yamllint`.
   - Strict Pydantic models: `frozen=True`, `extra="forbid"`, every field has `description="..."`, no raw dataclasses.
   - No `typing.Any` across type annotations; `disallow_untyped_defs = true`, `warn_return_any = true`.
   - Local uv-based `.pre-commit-config.yaml` using system interpreters from the virtual environment.
   - Pytest convention: live/network tests marked with `@pytest.mark.integration` and deselected by default via `addopts = ["--strict-markers", "-m", "not integration"]`.
3. **Repository Ecosystem & Language Diversity**:
   - `CATChem` (Community Atmospheric Transport & Chemistry): Fortran 90/2003/2008, C, CCPP physics scheme interfaces, CMake. Common review topics: chemical kinetics, photolysis rates, aerosol size distributions, memory management, CCPP metadata headers.
   - `CECE` (Chemistry Evaluation & Verification Engine): Fortran, C++, NetCDF interfaces, CMake. Common review topics: driver coupling, time-stepping, driver state initialization.
   - `ufs-chem-container`: Dockerfile, Apptainer/Singularity recipes, bash scripts, Spack specs. Common review topics: container layer optimization, environment variables, compiler flags, non-root user permissions.
   - `ufs-chem-assay`: Python 3.11+, pytest combinatorial suites, xarray, cartopy, pydantic, Slurm HPC runner scripts. Common review topics: harness test isolation, baseline verification, S3 data staging.
   - `HELM-Project`: Atmospheric chemistry workflows, Python, Shell, YAML configs. Common review topics: job orchestration, runtime environment configuration.
4. **Ponytail Review Skill Analysis**:
   - Reviewed from `/Users/bkoziol/.gemini/config/plugins/ponytail/skills/ponytail-review/SKILL.md`.
   - Core philosophy: Review for over-engineering only, not correctness.
   - One line per finding: `L<line>: <tag> <what to cut>. <replacement>.`
   - Canonical Tags:
     - `delete`: dead code, speculative features, unused parameters or imports.
     - `stdlib`: reinventing what standard libraries provide.
     - `native`: third-party dependency doing what the core language or platform already does.
     - `yagni`: unnecessary abstraction with only one implementation or speculative generality.
     - `shrink`: same logic expressed in fewer lines and less complexity.
   - Metric: Net lines and dependencies removable. If lean: `"Lean already. Ship."`
5. **GitHub Review API Mechanics**:
   - POST `/repos/{owner}/{repo}/pulls/{pull_number}/reviews`:
     - `commit_id`: SHA of the commit being reviewed.
     - `body`: Markdown review summary.
     - `event`: `"APPROVE"`, `"REQUEST_CHANGES"`, or `"COMMENT"`.
     - `comments`: list of objects with `path`, `line`, `side` (`"RIGHT"`), `body`.
   - GraphQL API v4: Pull request review threads (`PullRequestReviewThread`) provide `isResolved`, comments list, line numbers, and original commits.
   - Tracking diff follow-ups: When a review comment is created at timestamp `t`, subsequent commits in the PR (`commit.timestamp > t`) can be compared against the file and line range of the comment. If the lines were modified or deleted, `has_diff_followup = True`.

## Design

### 0. Decisions

- **Package & Dependency Strategy**:
  - `python>=3.11`.
  - Dependencies: `mcp>=1.12,<2`, `pydantic>=2.7`, `pydantic-settings>=2.2`, `httpx>=0.27` (async HTTP client with connection pooling for GitHub API), `pyyaml>=6.0`.
  - Dev dependencies: `pytest>=8.0`, `pytest-mock>=3.14`, `pytest-cov>=5.0`, `pytest-asyncio>=0.23`, `respx>=0.21` (mocking httpx requests), `mypy>=1.14`, `ruff>=0.12,<0.13`, `pre-commit>=4.0`, `yamlfix>=1.16`, `yamllint>=1.35`.
  - Build system: `hatchling` with project layout `src/ufs_chem_pr_review_mcp/`.
- **Database Engine: SQLite with FTS5 (`sqlite3`)**:
  - Standard library, zero external server requirement, local single-file database (`data/ufs_chem_reviews.sqlite3`).
  - Full-Text Search via SQLite FTS5 extension enables sub-millisecond keyword and fuzzy matching across thousands of historical review comments.
  - Automatic indexing on `repo`, `language`, `category`, `criticality`, `has_diff_followup`, and `created_at`.
- **Ingestion & Serving Separation**:
  - `src/ufs_chem_pr_review_mcp/server.py`: Fast, read-only MCP server over STDIO. Opens SQLite with `PRAGMA query_only = ON;`.
  - `src/ufs_chem_pr_review_mcp/cli/sync.py`: Standalone CLI entrypoint (`ufs-chem-pr-review-sync`) for pulling new comments, running diff follow-up detection, and pruning stale records.
- **Classification Taxonomy**:
  - Categories:
    - `overengineering`: Ponytail violations (dead code, excessive abstraction, reinvented wheel).
    - `correctness`: Off-by-one, memory leaks, uninitialized variables, array bounds, pointer bugs.
    - `chemistry_physics`: Unit mismatches (ppmv vs kg/kg, STP vs ambient), molecular weights, emission factors, photolysis indices, mass conservation.
    - `esmf_nuopc`: NUOPC Cap conventions, ESMF state sharing, field dictionary naming, grid discretization mismatches.
    - `concurrency_hpc`: MPI communication deadlocks, OpenMP race conditions, memory bandwidth, GPU/Kokkos offloading caveats.
    - `build_packaging`: CMake dependencies, Spack specs, Dockerfile layers, compiler incompatibility.
    - `ci_testing`: Test coverage, harness integration, baseline drift.
    - `style_docs`: Conventions, naming, formatting.
  - Criticality Scale:
    - `5` (Blocker / Bug / Crash): Calculation error, deadlock, invalid chemistry, memory corruption.
    - `4` (Major): Logic flaw under specific boundary conditions, memory leak, unverified physical units.
    - `3` (Moderate): Over-engineering, poor performance, missing error checks.
    - `2` (Minor): Style inconsistency, missing comments or docs.
    - `1` (Nit): Formatting, typo.
- **Client LLM Parsing Role**:
  - The MCP server does **not** make LLM calls. It extracts the PR diff, retrieves matching historical review comments, applies regex/AST-based ponytail checks and domain heuristics, and returns a rich, structured Pydantic-validated JSON payload.
  - The user's client LLM reads this structured context, reviews the PR diff with grounded historical evidence, and produces the final review comments in either GitHub Review API JSON format or GitHub Markdown.
- **Coverage & Test Isolation Policy**:
  - 100% line and branch coverage required for all mock unit tests via `pytest-cov --cov=src/ufs_chem_pr_review_mcp --cov-fail-under=100`.
  - Integration tests calling real GitHub endpoints require `@pytest.mark.integration` and are deselected by default in `pytest.ini_options` via `addopts = ["--strict-markers", "-m", "not integration"]`.

### 3. Database & Full-Text Search (SQLite & FTS5)

SQLite schema is stored in `src/ufs_chem_pr_review_mcp/db/schema.py` and initialized on first launch.

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;

CREATE TABLE IF NOT EXISTS repositories (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL UNIQUE,
    url TEXT NOT NULL,
    default_branch TEXT NOT NULL DEFAULT 'main',
    last_synced_at TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS pull_requests (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    repo_id INTEGER NOT NULL REFERENCES repositories(id) ON DELETE CASCADE,
    pr_number INTEGER NOT NULL,
    title TEXT NOT NULL,
    author_login TEXT NOT NULL,
    state TEXT NOT NULL,
    base_sha TEXT NOT NULL,
    head_sha TEXT NOT NULL,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    merged_at TEXT,
    indexed_at TEXT NOT NULL,
    UNIQUE(repo_id, pr_number)
);

CREATE TABLE IF NOT EXISTS review_comments (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    pr_id INTEGER NOT NULL REFERENCES pull_requests(id) ON DELETE CASCADE,
    comment_node_id TEXT NOT NULL UNIQUE,
    author_login TEXT NOT NULL,
    author_association TEXT NOT NULL,
    body TEXT NOT NULL,
    path TEXT NOT NULL,
    line INTEGER,
    original_line INTEGER,
    diff_hunk TEXT,
    language TEXT NOT NULL,
    category TEXT NOT NULL,
    criticality INTEGER NOT NULL CHECK(criticality BETWEEN 1 AND 5),
    has_diff_followup INTEGER NOT NULL CHECK(has_diff_followup IN (0, 1)),
    diff_followup_status TEXT NOT NULL,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    indexed_at TEXT NOT NULL
);

-- Indices for rapid structured querying
CREATE INDEX IF NOT EXISTS idx_comments_path ON review_comments(path);
CREATE INDEX IF NOT EXISTS idx_comments_language ON review_comments(language);
CREATE INDEX IF NOT EXISTS idx_comments_category ON review_comments(category);
CREATE INDEX IF NOT EXISTS idx_comments_criticality ON review_comments(criticality);
CREATE INDEX IF NOT EXISTS idx_comments_has_diff_followup ON review_comments(has_diff_followup);
CREATE INDEX IF NOT EXISTS idx_comments_created_at ON review_comments(created_at);
CREATE INDEX IF NOT EXISTS idx_comments_author ON review_comments(author_login);

-- Full-Text Search 5 virtual table for comment body, path, diff hunk
CREATE VIRTUAL TABLE IF NOT EXISTS comments_fts USING fts5(
    body,
    path,
    diff_hunk,
    content='review_comments',
    content_rowid='id'
);

-- Triggers to maintain FTS consistency
CREATE TRIGGER IF NOT EXISTS comments_ai AFTER INSERT ON review_comments BEGIN
  INSERT INTO comments_fts(rowid, body, path, diff_hunk) VALUES (new.id, new.body, new.path, new.diff_hunk);
END;

CREATE TRIGGER IF NOT EXISTS comments_ad AFTER DELETE ON review_comments BEGIN
  INSERT INTO comments_fts(comments_fts, rowid, body, path, diff_hunk) VALUES('delete', old.id, old.body, old.path, old.diff_hunk);
END;

CREATE TRIGGER IF NOT EXISTS comments_au AFTER UPDATE ON review_comments BEGIN
  INSERT INTO comments_fts(comments_fts, rowid, body, path, diff_hunk) VALUES('delete', old.id, old.body, old.path, old.diff_hunk);
  INSERT INTO comments_fts(rowid, body, path, diff_hunk) VALUES (new.id, new.body, new.path, new.diff_hunk);
END;
```

#### Pruning Mechanics (`src/ufs_chem_pr_review_mcp/db/pruning.py`)
- Database pruning function `prune_database(conn: sqlite3.Connection, retention_days: int | None = None, max_records_per_repo: int | None = None) -> int`.
- Safely removes stale closed unmerged PRs or comments older than the retention threshold using `created_at` and `indexed_at`.
- Cascading foreign keys ensure children in `review_comments` and FTS index entries are cleaned automatically.

### 4. GitHub Ingestion & Refresh Engine

#### `src/ufs_chem_pr_review_mcp/ingest/client.py`
- Built on `httpx.AsyncClient` with authentication via `GITHUB_TOKEN` environment variable.
- Supports both REST API (`/repos/{owner}/{repo}/pulls`, `/pulls/{pull_number}/comments`, `/pulls/{pull_number}/commits`) and GraphQL API for review thread status (`PullRequestReviewThread.isResolved`).
- Handles GitHub API rate limits transparently:
  - Checks `X-RateLimit-Remaining` and `X-RateLimit-Reset` headers.
  - Implements exponential backoff on HTTP 403 / 429.
  - Implements HTTP ETag conditional requests (`If-None-Match`) to avoid consuming rate limit quota on unchanged resources.

#### `src/ufs_chem_pr_review_mcp/ingest/diff_tracker.py`
Follow-up diff association engine:
1. For each review comment at timestamp $T_{\text{comment}}$ referencing file $P$ and diff line $L$:
2. Query commits in the PR where $T_{\text{commit}} > T_{\text{comment}}$.
3. Fetch the commit file patches. If any subsequent commit touches file $P$ within a window of $L \pm 10$ lines (or deletes the referenced code block):
   - `has_diff_followup = True`
   - `diff_followup_status = DiffFollowUpStatus.CODE_MODIFIED`
4. If no subsequent commit touches file $P$, inspect subsequent thread replies:
   - If author replied with explanation or resolved thread: `DiffFollowUpStatus.REJECTED_EXPLAINED` or `DiffFollowUpStatus.DISCUSSION_ONLY`.
   - If no reply: `DiffFollowUpStatus.NO_RESPONSE`.
   - `has_diff_followup = False`.

#### `src/ufs_chem_pr_review_mcp/ingest/classifier.py`
Automated categorization and criticality ranking without requiring an LLM:
1. **Language Detection**: Derived from file extension (`.F90`, `.f90`, `.inc` $\rightarrow$ Fortran; `.cpp`, `.hpp`, `.cc` $\rightarrow$ C++; `.py` $\rightarrow$ Python; `CMakeLists.txt`, `.cmake` $\rightarrow$ CMake; `Dockerfile`, `Containerfile` $\rightarrow$ Dockerfile; `.sh`, `.bash` $\rightarrow$ Shell; `.yaml`, `.yml` $\rightarrow$ YAML).
2. **Category Classification**: Deterministic regex and keyword matching over the comment body:
   - `chemistry_physics`: keywords `unit`, `ppm`, `ppb`, `kg/kg`, `molar`, `molecular weight`, `emission`, `aerosol`, `photolysis`, `stoichiometry`, `half-life`, `reaction rate`.
   - `esmf_nuopc`: keywords `nuopc`, `esmf`, `cap`, `advertise`, `realize`, `importstate`, `exportstate`, `field dictionary`, `coupling`, `clock`, `alarm`.
   - `concurrency_hpc`: keywords `mpi_`, `openmp`, `thread`, `deadlock`, `barrier`, `race condition`, `kokkos`, `offload`, `cuda`, `gpu`, `bandwidth`.
   - `overengineering`: keywords `yagni`, `over-engineered`, `unused`, `dead code`, `unnecessary abstraction`, `wrapper`, `simplify`, `boilerplate`, `native`.
   - `correctness`: keywords `bug`, `crash`, `segfault`, `out of bounds`, `uninitialized`, `leak`, `memory leak`, `null`, `nullptr`, `nan`, `infinity`, `off-by-one`.
   - `build_packaging`: keywords `cmake`, `spack`, `compiler`, `docker`, `container`, `target_link_libraries`, `find_package`, `build error`.
   - Default fallback: `style_docs`.
3. **Criticality Ranking (1 to 5)**:
   - Score 5: Mentions crash, segfault, invalid physics/chemistry, data corruption, security vulnerability, AND has `has_diff_followup = True`.
   - Score 4: Mentions memory leak, uninitialized variable, off-by-one, deadlock, or test failure AND has `has_diff_followup = True`.
   - Score 3: Performance, over-engineering / simplification suggestions, missing edge cases.
   - Score 2: Minor refactoring, naming conventions, documentation gaps.
   - Score 1: Whitespace, spelling, trivial style nits.

### 5. Review Context Classification & Ponytail Analysis

#### `src/ufs_chem_pr_review_mcp/rules/ponytail.py`
Static rule engine inspired by the `ponytail-review` skill, executed directly against diff hunks:
- **`delete` Rule**:
  - Unused imported symbols (Python `import`, Fortran `use ... only:`, C++ `#include`).
  - Commented-out dead code blocks in new additions.
  - Speculative utility functions added without any call site in the PR diff.
- **`stdlib` Rule**:
  - Reimplementing standard library routines (e.g., custom string splitting, home-grown min/max or sorting, custom path concatenation when `pathlib` / `std::filesystem` exists).
- **`native` Rule**:
  - Introducing heavy dependencies for trivial operations (e.g. adding a 3rd party package for basic JSON parsing or math calculations).
- **`yagni` Rule**:
  - Single-implementation abstract base classes / interfaces.
  - Factory functions or strategy patterns where only one concrete variant exists.
  - Speculative configuration flags or CLI parameters not referenced anywhere in execution logic.
- **`shrink` Rule**:
  - Verbose boilerplate that can be collapsed into standard idiomatic constructs (e.g., Python list comprehensions, ternary operators, modern Fortran array syntax `a(:) = 0.0`).
- **Formatting**:
  - Emits `PonytailFinding` objects with exact line numbers, tags, cut descriptions, replacements, and lines saved.
  - If no findings exist: `"Lean already. Ship."`

#### `src/ufs_chem_pr_review_mcp/rules/ufs_chem.py`
Specialized domain rules for UFS atmospheric chemistry code:
- **Atmospheric Chemistry Units**:
  - Flags conversions between molar mixing ratios (mol/mol, ppmv, ppbv) and mass mixing ratios (kg/kg) lacking molecular weight normalization ($M_{\text{spec}} / M_{\text{air}}$ where $M_{\text{air}} \approx 28.964 \text{ g/mol}$).
  - Flags emissions calculations missing grid cell area or timestep scaling.
- **ESMF / NUOPC Cap Correctness**:
  - Flags `ESMC_StateGet` / `ESMF_StateGet` calls lacking proper return code checks (`ESMF_LogFoundError`).
  - Verifies that advertised fields are realized before state exchanges.
- **Fortran Numerical & HPC Safety**:
  - Flags single-precision literals (e.g. `1.0` instead of `1.0_rk` or `1.0d0`) in double-precision floating-point chemistry calculations.
  - Flags array dimension order in nested loops that violate Fortran column-major memory ordering (outer loop over first index, inner loop over last index $\rightarrow$ cache thrashing).
  - Flags allocate statements without `stat=` and `errmsg=` checks.

### 6. MCP Server Protocol, Tools, Resources & Prompts

The server runs on STDIO via `mcp.server.stdio` and uses the standard `Server("ufs-chem-pr-review-mcp")`.

#### MCP Tools Exposed:

1. **`evaluate_pr`**:
   - **Description**: "Evaluates a GitHub pull request in a UFS-Chem repository. Parses the PR diff, retrieves matching historical review comments, runs automated ponytail over-engineering audits and domain checks, and returns structured context for client LLM review synthesis."
   - **Input Schema**: `EvaluatePrInput` (repo, pr_number, output_format, include_ponytail_audit, max_context_comments).
   - **Return**: `ReviewContextResponse` as serialized JSON.
2. **`evaluate_diff`**:
   - **Description**: "Evaluates an uncommitted or local git diff text. Matches historical review comments from similar files in UFS-Chem repos, runs ponytail and domain audits, and provides structured review context for client LLM synthesis."
   - **Input Schema**: `EvaluateDiffInput` (diff_text, target_repo, output_format, include_ponytail_audit, max_context_comments).
   - **Return**: `ReviewContextResponse`.
3. **`search_review_history`**:
   - **Description**: "Performs full-text search across historical review comments and threads from CATChem, CECE, ufs-chem-container, ufs-chem-assay, and HELM-Project. Filters by language, category, reviewer, and whether comments prompted code changes."
   - **Input Schema**: `SearchReviewHistoryInput` (query, repo, language, category, min_criticality, has_diff_followup_only, limit).
   - **Return**: `list[ReviewCommentRecord]`.
4. **`get_repo_review_stats`**:
   - **Description**: "Retrieves review statistics for a UFS-Chem repository: total indexed PRs, comments, top reviewers, common caught categories, and diff follow-up acceptance rates."
   - **Input Schema**: `{"repo": str}`.
   - **Return**: `dict[str, Any]` (safe JSON object containing repo metrics).
5. **`format_review_output`**:
   - **Description**: "Helper tool that converts structured review findings and critical summaries into GitHub Review API JSON payload or formatted GitHub Markdown."
   - **Input Schema**:
     - `findings`: list of findings (path, line, body, category, criticality).
     - `critical_summary`: overarching review summary string.
     - `output_format`: `github_json` | `markdown` | `both`.
   - **Return**: Formatted string or JSON object matching `GitHubReviewPayload`.

#### MCP Resources Exposed:

- `ufs-chem://repositories`: JSON listing of all configured repositories, tracked branches, and last sync timestamps.
- `ufs-chem://guidelines/{category}`: Markdown guidelines and common reviewer pitfalls for specific review categories (`ponytail`, `chemistry_physics`, `esmf_nuopc`, `fortran_standards`).

#### MCP Prompts Exposed:

- `review_pr`:
  - **Arguments**: `repo` (str), `pr_number` (int), `output_format` (str, default `"markdown"`).
  - **Prompt Body**:
    Instructs the LLM:
    1. Call `evaluate_pr` to retrieve the diff, ponytail over-engineering findings, domain rules, and historical review comments.
    2. Examine any `ponytail` findings: evaluate dead code, unnecessary abstractions, and lines removable.
    3. Examine any `chemistry_physics` findings: verify unit consistency (ppm vs kg/kg, STP vs ambient), molecular weights, and conservation.
    4. Cross-reference historical review comments: notice how past PRs in this repo handled similar diff patterns and whether reviewers caught recurring issues.
    5. Generate the review output in the requested format (`output_format`):
       - If `github_json`: Output valid JSON adhering to `GitHubReviewPayload` with `event` (`COMMENT` or `REQUEST_CHANGES`), overarching `body`, and inline `comments`.
       - If `markdown`: Output clean GitHub Markdown with a Critical Summary section, followed by inline file/line recommendations.
       - Always include the Critical Summary.

### 9. Edge Cases, Guards & Error Handling

1. **GitHub API Rate Limits**:
   - `httpx` client checks remaining quota on each call. If unauthenticated (`GITHUB_TOKEN` is None), logs a clear warning explaining that GitHub restricts unauthenticated traffic to 60 requests/hr.
   - Reuses HTTP ETags for unchanged PR threads so incremental polling consumes minimal quota.
2. **Large PR Diffs**:
   - Giant PRs touching generated code or third-party vendored bundles (e.g. large NetCDF test files or Fortran build artifacts) can overwhelm LLM context windows.
   - Server ignores binary files and truncates diff hunks per file to a configurable maximum (e.g. 1000 lines), warning the caller.
3. **Outdated or Displaced Review Comments**:
   - When files are renamed or refactored in later commits, GitHub marks line comments as outdated.
   - The sync engine records `original_line` alongside `line` and stores the `diff_hunk` snippet, ensuring search remains accurate even when the file structure shifts.
4. **Offline Local Usage**:
   - The MCP server operates completely offline when evaluating local diffs or reading existing indexed reviews. A missing network or expired GitHub token only prevents active syncing, never local review context retrieval.
5. **Database Concurrency & Locking**:
   - SQLite WAL mode (`PRAGMA journal_mode = WAL;`) allows concurrent read-only queries from multiple MCP client processes while an incremental background sync writes updates.
   - The MCP server sets `PRAGMA query_only = ON;` upon connection to prevent unintentional database modifications during tool serving.

## Risks and notes

- **Zero LLM Boundary**: The MCP server strictly delivers parsed diffs, classified historical comments, and deterministic rule findings. It leaves final linguistic synthesis and comment formatting to the user's client LLM. This prevents token costs and latency inside the server.
- **GitHub Token Security**: `GITHUB_TOKEN` is read from the environment or `.env` and is never logged or exposed via MCP tool outputs.
- **Diff Follow-up Accuracy**: Some PRs squash commits or make wholesale refactors that obscure individual comment line resolutions. The diff tracker uses a $\pm 10$ line window and thread resolution status to provide resilient classification.
- **Database Portability**: The committed SQLite database contains pre-indexed comments from the 5 repositories so fresh clones can run the MCP server immediately without requiring initial sync downloads.

---

## Resolved decisions

1. **MCP SDK**: `mcp>=1.12,<2` selected, matching `omd-docs-mcp`.
2. **Storage Engine**: SQLite with FTS5 virtual tables (`sqlite3` stdlib) selected for zero external runtime dependencies and instant local search.
3. **No Local LLM**: The server does not host or execute an LLM. Structured JSON/Markdown outputs are prepared for the client agent.
4. **Coverage Standard**: 100% mock test coverage enforced in CI (`pytest-cov --cov-fail-under=100`); live network tests marked `integration` and deselected by default.
5. **Ponytail Integration**: Integrated as a static heuristic engine checking diff hunks for `delete`, `stdlib`, `native`, `yagni`, `shrink`, and line reduction metrics.
6. **Follow-up Diff Metric**: Tracked per comment by checking subsequent commits against modified line ranges, classifying comments into actionable catches vs discussion.

## requirements

- use https://github.com/bbakernoaa/omd-docs-mcp as an example. mostly for the packages it uses.
- the goal is to develop an mcp server that can perform an initial review of ufs-chem repositories
  - input will be the current pr to evaluate
  - output will be json suitable to post directly to github or markdown that a user can use to post their own comments
  - a critical summary should always be returned
  - users should be able to run the server locally and use it to evaluate their own prs. hence, it should be easy to run locally against a pr they've created on github
  - their chosen llm can select what output they want
- there are the repositories we'll want to scan focusing on pr comments and associated responses and diff follow-ups:
  - https://github.com/ufs-community/CATChem
  - https://github.com/ufs-community/CECE
  - https://github.com/ufs-community/ufs-chem-container
  - https://github.com/benkozi/ufs-chem-assay
  - https://github.com/bbakernoaa/HELM-Project/
- we'll want to include a metadata context for each comment: what language, what repository, did the comment actually have a diff associated with it after posting (basically did the use respond; a ranking for how critical the catch was)
- add pre-commit following https://github.com/benkozi/ufs-chem-assay
- make sure we incorporate a refresh capability
- the source repository paths may change over time so make that configurable
- add a weekly ci job to refresh the database
- ensure all code passes mock tests; add a ci job that fails if code coverage is not 100%
  - "integration" tests can be excluded from this. any tests with live connections should be tagged with an "integration" marker
- incorporate any well-known code review skills on the web (i.e. ponytail)
- we want the context provided to the user's chosen llm to be easily parsable since the mcp server here will not run any llm
- the goal is to provide the user's llm with a context to evaluate, so this mcp server should identify a way to classify the contexts of the code review comments and return useful information
- track what github user make the comment
- spend some time iterating on what would be useful. feel free to make llm calls on the code review context to flesh things out
- the database may eventually need to be pruned so record datetime stamps for each record
