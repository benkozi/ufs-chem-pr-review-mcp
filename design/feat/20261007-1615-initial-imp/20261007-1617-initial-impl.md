# requirements

- use https://github.com/bbakernoaa/omd-docs-mcp as an example. mostly for the packages it uses.
- the goal is to develop an mcp server that can perform an initial review of ufs-chem repositories
  - input will be the current pr to evaluate
  - output will be json suitable to post directly to github or markdown that a user can use to post their own comments
  - a critical summary should always be returned
  - users should be able to run the server locally and use it to evaluate their own prs. hence, it should be easy to run locally against a pr they've created on github
  - their chosen llm can select what output they want
- there are the repositories we'll want to scan focusing on pr comments and associated responses and diff follow-ups:
  - https://github.com/ufs-community/CATChem
  - https://github.com/ufs-community/CECE
  - https://github.com/ufs-community/ufs-chem-container
  - https://github.com/benkozi/ufs-chem-assay
  - https://github.com/bbakernoaa/HELM-Project/
- we'll want to include a metadata context for each comment: what language, what repository, did the comment actually have a diff associated with it after posting (basically did the use respond; a ranking for how critical the catch was)
- add pre-commit following https://github.com/benkozi/ufs-chem-assay
- make sure we incorporate a refresh capability
- the source repository paths may change over time so make that configurable
- add a weekly ci job to refresh the database
- ensure all code passes mock tests; add a ci job that fails if code coverage is not 100%
  - "integration" tests can be excluded from this. any tests with live connections should be tagged with an "integration" marker
- incorporate any well-known code review skills on the web (i.e. ponytail)
- we want the context provided to the user's chosen llm to be easily parsable since the mcp server here will not run any llm
- the goal is to provide the user's llm with a context to evaluate, so this mcp server should identify a way to classify the contexts of the code review comments and return useful information
- track what github user make the comment
- spend some time iterating on what would be useful. feel free to make llm calls on the code review context to flesh things out
- the database may eventually need to be pruned so record datetime stamps for each record
